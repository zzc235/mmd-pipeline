# 1. 接手模型的统一工作纪律

## 1.1 每个阶段的固定输出

每个阶段结束都必须写一份独立报告，建议路径：

```text
reports/coordination/<YYYYMMDD>_<阶段名>_<执行者>.md
```

报告至少包含：

- 阶段名、执行者、开始/结束时间；
- 主仓库 HEAD、所用 worktree HEAD、base；
- 执行前 `git status --short --branch`；
- 每条命令、工作目录、退出码；
- board 操作前后 SHA256（只要碰了 board 命令）；
- 测试发现数、失败数、跳过数、最终 OK/FAIL；
- 新增/修改文件清单；
- 实测结论与**不能主张的结论**；
- 下一阶段是否解锁；未解锁时写清 `NEEDS_HUMAN` 的具体问题。

## 1.2 状态词只允许这样使用

| 状态词 | 使用条件 |
|---|---|
| `PASS` | 本阶段全部判据有实测输出且通过 |
| `FAIL` | 判据执行了但不满足；保留完整错误，停止后续阶段 |
| `BLOCKED` | 前置未满足，当前阶段不能开始或不能继续 |
| `NEEDS_HUMAN` | 涉及提交边界、合并、丢弃提交、全局配置、生产启动、规格变更 |
| `UNMEASURED` | 没跑过；不得用“理论上可过”替代 |

## 1.3 通用停止条件

出现任何一条，立即停止并交回 Human/D0：

- HEAD、worktree 分叉或 dirty 状态与本阶段前置不符；
- 只读命令前后 board SHA256 改变；
- `status --check` 非 OK、`taxonomy --check` 非 OK、`sync_board --mode check` 非 OK；
- 测试发现数无合理原因偏离当前 940；
- 同一输出目录/run_id 已存在且非空；
- base 不在 HEAD 祖先链、HEAD 与声明不符、worktree dirty；
- Blender 锁被他人持有、锁状态残缺、心跳异常、lock_lost 非空；
- 需要删除旧产物才能继续；
- 需要绕过 preflight、`--no-lock`、`--allow-dirty` 或证据闸门才能继续；
- 需要修改业务期望值、历史裁决、冻结 manifest 才能转绿。

**禁止用连续重试代替定位。连续三次同类报错后，保留现场并停止。**

## 1.4 如果接手模型使用 Git Bash

本文命令默认 PowerShell。Git Bash 下必须改写，不得混用：

- Windows 路径写成 `E:/dsh pr/woker2`，原生 exe 不使用 `/e/...` 猜路径；
- 环境变量用 `PYTHONUTF8=1 python ...`，不是 `$env:PYTHONUTF8`；
- PowerShell 反引号续行不能照搬；在 Bash 中用反斜杠续行或写单行；
- 哈希可用 `sha256sum "E:/dsh pr/woker2/out/subai/coordination/board.db"`；
- 不要用 Python 读取 `/tmp/...` 或 `/c/...` 虚拟路径，传 `C:/...`、`E:/...` 形式。

核心测试的 Bash 形状：

```bash

```

无论使用哪个终端，都不要用 shell 重写中文源码；源码修改使用专用编辑工具。不要生成含中文路径的 `.ps1`/`.bat` 临时脚本，PowerShell 5.1 编码容易破坏文件名。

## 6.2 推荐处置方向（需 Human 批准）

6. 不删除旧树、不 rebase 重写既有证据归属，除非 Human 明确批准。

当前 dispatcher 只看 board 的 ready/deps/resource，没有验证每个席位的实际 worktree。应新增只读资格预检：

- 显式 lane/agent → worktree 映射，不允许靠猜路径；
- worktree 必须是 Git 根；
- worktree clean；
- 实际 HEAD 与计划声明一致；
- 计划 base 必须在 HEAD 祖先链；
- 不合格时输出明确 `PROVENANCE_INVALID` / `OWNERSHIP_VIOLATION` 和 Human 处置信息；
- 不得把不合格输出成 `idle`，更不得继续 `claim`；
- 不得自动 merge/rebase/fetch 来“修好”资格。

至少新增四类回归：

1. 合格 worktree 才允许 claim；
2. base 非祖先时拒绝；
3. dirty worktree 拒绝；
4. 缺配置/路径不存在时 fail-closed，而不是 idle。

**run_task 的最后一道 base 闸门已有测试，但它不能代替 dispatcher 提前拒绝错误派工。**

# 7. S4：board 在线备份与临时恢复演练

## 7.1 为什么现有快照不够

当前有两份改造前快照且哈希真实匹配，但 board 是运行时唯一权威，包含 events、run_id、队列、artifact 等。`task_status.json` 不能完整重建这些信息。

## 7.2 禁止的备份方式

- 正在写入时只复制 `board.db`，忽略 `board.db-wal`；
- 把“源 db 与备份 db 原始 SHA256 必须相同”当唯一正确性判据；
- 用真实 board 做恢复覆盖演练；
- 用 `--allow-resync` 冒充备份恢复。

SQLite 在线备份的逻辑一致性不等于两个数据库文件的物理字节完全相同。

## 7.3 实现要求

新增备份工具时应：

- 使用 SQLite 标准 backup API 或等价的在线一致备份；

## 7.4 恢复演练

只在临时目录恢复，验收：

1. `PRAGMA integrity_check` 返回 ok；
2. 逻辑表计数与备份 manifest 一致；

**真实恢复只能在 Human 确认当前 board 不再需要、并已另存当前状态后执行；本阶段不做真实覆盖。**

# 12. evidence、D0 裁决与 merge：不要只跑到 RUN_OK

## 12.1 生产执行必须带 evidence

`run_task` 的 `--evidence` 在代码里可选，但生产验收流程必须提供。

- `RUN_OK` 只表示命令 rc=0；
- 没有 evidence 时，不等于 submitted，不等于 completed；
- 有 evidence 且 submit 成功，也只是 submitted/queued；
- 之后仍需 D0 verify、受控裁决、merge；
- 不得直接 SQL 把任务改 completed。

## 12.2 标准状态流

```text
ready/returned
→ claimed
→ running
→ submitted 或 queued_submission
→ verifying
→ ACCEPT_MERGE: verified → merge queue → completed
→ RETURN_FIX: returned 或 blocked
→ BLOCK: blocked
→ NEEDS_HUMAN: needs_human
```

命令失败的新契约：

```text
running → RUN_FAILED 事件 → blocked + 清 owner + 释放资源
```

**blocked 后不得自动重试，也不得直接 `scheduler start` 硬推。先由 D0/Human 决定后续合法状态迁移。**

## 12.3 evidence 注意事项

- evidence/1 schema、files/tests/artifacts/known_risks 完整；
- `truth_tier` 与实际证据范围一致；
- `cache_replay` 不得声称 T2/T3；
- 文本 hash_basis 与 raw hash 分列，不混用；
- artifact 快照存原字节，只写不改；
- 同 artifact_id 不同字节必须新建 ID，不得覆盖；
- base/head、files[] 覆盖与实际 git diff 一致；
- 老证据不回填、不重写历史哈希。
