## 3. 逐项改动、原因与代码落点

### 3.1 board：只读视图不再偷偷建库

**文件**：`coordination/board.py`
**落点**：`Board.__init__` L132-154，`init()` L156-163

改动：

- 新增 `readonly=True`：用 SQLite URI `mode=ro` 打开；
- 只读模式不 `makedirs`、不执行 schema 初始化；
- 只读连接调用 `init()` 直接抛 `BOARD_READONLY`。

**原因**：原来的 `scheduler status/events`、`dispatcher`、`status --check` 都会实例化 Board 并写库。
如果路径错了，查询命令会造一个空 board，正是此前“空库冒充空闲”的同族问题。

**风险**：低；只影响视图入口，动作入口仍显式 `init()`。

---

### 3.2 board：运行号由唯一入口发放

**文件**：`coordination/board.py`
**落点**：`issue_run_id()` L195-205

改动：

- 新增 `Board.issue_run_id(task_id)`；
- 组成 `时间戳_TASK_8位随机hex`；
- 每次发号写一条 `RUN_ISSUED` 事件，可追溯。

**原因**：runner 原 run_id 只精确到秒，同秒两次运行会同目录；靠调用方自己拼字符串无法防止。
运行号必须来自唯一状态权威，且要留下事件。

**风险**：低；事件表 append-only，不改任务状态。

---

### 3.3 board：artifact 不可变

**文件**：`coordination/board.py`
**落点**：`_put_artifact()` L222-241，`add_artifact()` L242-248，`merge_done()` 内调用

改动：

- 同 artifact_id 同字段：幂等；
- 同 artifact_id 不同路径/sha/版本/acceptance：抛 `SNAPSHOT_INVALID`；
- `merge_done()` 不再用 `INSERT OR REPLACE`。

**原因**：已验收 artifact 是物证。覆盖后，历史裁决里的 sha 会永久失效，
与 `evidence_store.py` 的“快照只写不改”原则相冲突。

**风险**：中；如果历史脚本故意想覆盖 artifact，现在会红。但这是期望行为，改 artifact 必须新建 ID。

---

### 3.4 board：依赖允许“只依赖任务完成”

**文件**：`coordination/board.py`
**落点**：`_deps_ok()` L300-321

改动：

- `deps.artifact` 为空时，只检查上游任务是否 `completed`；
- 给了 artifact 路径时，仍校验产物存在、sha 与 required_sha。

**原因**：当前真实依赖是模块级完成关系，很多任务没有唯一 artifact 路径。
旧实现把空 artifact 当成“查不到产物”，使依赖图无法表达。

**风险**：中；依赖粒度仍是模块级，不是原子任务级，见“残余风险”。

---

### 3.5 board：returned 任务可重新认领

**文件**：`coordination/board.py`
**落点**：`_pick_ready()` L325-329，`claim()` 内 UPDATE

改动：

- `_pick_ready()` 从 `status='ready'` 扩到 `ready/returned`；
- `claim()` 的原子 UPDATE 同步允许这两个状态。

**原因**：`RETURN_FIX` 把任务置为 `returned`，但 `claim()` 只挑 `ready`，
导致一次打回后任务无人能再领，除非外部手写状态。这是会永久卡死流水线的状态机洞。

**风险**：低；有回归测试钉住。

---

### 3.6 board：无依赖的 blocked 不再被误解锁

**文件**：`coordination/board.py`
**落点**：`_recompute_deps()` L605-625

改动：

- 只遍历 `deps` 表里真实登记依赖的任务；
- 没有依赖记录的 blocked 任务保持 blocked。

**原因**：旧实现对所有 blocked 任务调用 `_deps_ok()`，而“没有依赖”恒满足，
于是任何一次 merge 都可能把所有 PARTIAL/Human 阻塞任务一起洗成 ready。

**风险**：低；有回归测试钉住。

---

### 3.7 board：提交前先做便宜检查

**文件**：`coordination/board.py`
**落点**：`submit()` L394-460

改动：

- 先 validate、算 digest；
- 再检查任务存在、状态、队列、重复 hash；
- 只有这些通过才跑较贵的 gate/coverage；
- 事务内仍原子复核一次。

**原因**：DeepSeek V4.1 Flash 倾向频繁自检。重复证据、错误状态这类请求不该先跑完整闸门再被发现。

**风险**：低；重复 hash 仍由事务内唯一约束与显式检查共同保证。

### 3.8 sync_board：bootstrap 只能一次

**文件**：`coordination/sync_board.py`
**落点**：

- `load_task_graph()` L82
- `_ensure_bootstrap_table()` L98
- `record_bootstrap()` L112
- `_record_artifact()` L157
- `sync()` L191-323
- CLI mode L333-350

改动：

- 新增 `--mode bootstrap|check|verify`，默认 **check**；
- bootstrap 写 `sync_bootstrap` 表，记录 status/decisions 的 sha256；
- 重复 bootstrap 默认拒绝，只有 `--allow-resync` 才允许；
- check/verify 走只读连接，不迁移、不写事件；
- bootstrap 写入任务资源、依赖图，并调用 `recompute_deps()`；
- 历史 artifact 不覆盖，冲突只记事件。

**原因**：交接文档要求“bootstrap 只能成功一次”，旧实现默认反复覆盖。
同时，空 board 的修复必须是一次可审计动作，不能在日常 `--check` 中隐式发生。

**风险**：中；旧脚本若直接 `python -m coordination.sync_board` 期待写库，现在会只检查。

### 3.12 新增统一执行入口

**新文件**：`coordination/run_task.py`

主要函数：

- `verify_worktree()` L58：git 根、head、base 祖先、dirty 检查；
- `load_preflight_spec()` L99：递归展开 `{task_id}/{agent}/{run_id}/{worktree}`；
- `ensure_claim()` L108：认领/归属/状态校验；
- `execute_command()` L129：资源不是 none 时强制 `lock.guard`；
- `main()`：串起 claim → start → worktree → preflight → run_id → execute → submit。

**原因**：通用 `run_pipeline.py -> mmdpipe.runner` 原本完全不接 board/preflight/lock。
错树、cap 不足、无锁启动这些闸门只在 M04 等专用脚本里存在，不是全流程保证。

**关键约束**：

- `--` 之后是原始 argv 列表，不经 shell，避免中文路径和 `|` 被改写；
- `--dry-run` 不写 board、不占锁、不执行命令；
- 资源不是 none 且未给 `--no-lock` 时，owner 必须是 `模块|工作树`；
- 只在命令 rc=0 后才可选提交证据。

**风险**：中；当前没有自动收集 evidence，仍需调用方生成 `--evidence` JSON，
也没有 stage-level resume。见“残余风险”。
